1. **Database: SQLite instead of PostgreSQL.** No Docker/Postgres available in this
   environment. `prisma/schema.prisma` uses `datasource db { provider = "sqlite" }`.
   All model fields, `@@index`, `@default(uuid())`, and relations are unchanged from

   single shared SQLite file. `vitest.config.ts` sets `process.env.DATABASE_URL ||=

   manual exports) and keeps `fileParallelism: false`; `resetDb()` (truncation
   between tests) gives per-test isolation on that single file, exactly per the
   task instructions' suggested approach. Migration applied once via
   `DATABASE_URL="file:./dev.db" npx prisma migrate dev --name init`, generating
   `prisma/migrations/20260819091655_init/`.
2. **bcrypt (native) — no substitution needed.** The Windows/Node 22 pitfall did not
   occur here: `npm i bcrypt@5` installed and its native binary loaded and ran
   correctly (verified with a standalone hash/compare smoke test before wiring it
   into `src/lib/password.ts`). `bcryptjs` was NOT used; `src/lib/password.ts`
   imports `bcrypt` exactly as the plan specifies.
3. **tsconfig `types` extended with `"vitest/globals"`.** The plan's tsconfig only
   lists `"types": ["node"]`, but Vitest's `globals: true` config relies on ambient
   globals (`it`, `expect`, `beforeEach`) that aren't declared anywhere else. This
   doesn't affect `npm test` (Vitest transpiles via esbuild/vite, not `tsc`), but it
   made `tsc --noEmit` / `npm run build` fail with `Cannot find name 'it'` etc.
   across every test file. Fixed by changing `types` to `["node", "vitest/globals"]`
   in `tsconfig.json` — no other file touched, no plan-specified code changed.

No other deviations. All routes, verbs, JSON shapes, Zod schemas, JWT/bcrypt logic,
`@@index`, `@default(uuid())`, and response shapes match the plan verbatim.

## Fix report — post-review defects (2026-08-19)

The coordinator's final review found three real defects in the Task 1–7
implementation. All three are fixed below, two new tests were added per the
review's instructions, and the full suite + strict type-check were re-verified
green. Rate limiting and a `RevokedToken` purge job were explicitly out of
scope for this pass (deferred by ruling to the hardening plan / an ops cron)
and were not added.

### FIX 1 — hardcoded JWT secret fallbacks (`src/lib/tokens.ts`)

**Defect:** `process.env.JWT_ACCESS_SECRET ?? "dev-access"` and the refresh
equivalent meant a misconfigured deployment (missing env var) would silently
sign and verify tokens with a public, hardcoded value instead of failing.

**Fix:**
- Removed both fallbacks. The module now reads `JWT_ACCESS_SECRET` /
  `JWT_REFRESH_SECRET` from `process.env` and throws
  `Error("JWT_ACCESS_SECRET and JWT_REFRESH_SECRET must be set")` at import
  time if either is missing or empty — the app fails fast at boot instead of
  running with a guessable signing key.
- Because TypeScript's control-flow narrowing from the `if (!accessSecret ||
  !refreshSecret) throw` guard does not persist into the closures
  (`signAccess`, `signRefresh`, `verifyAccess`, `verifyRefresh`) defined
  afterward, the checked values are re-bound to explicitly-typed `const A:
  string` / `const R: string` immediately after the guard so `strict` mode
  type-checks cleanly — this is a type-level-only change, no behavior
  difference.
- Both `verifyAccess` and `verifyRefresh` now pin `{ algorithms: ["HS256"] }`
  on `jwt.verify`, closing the "alg confusion" class of JWT attacks (e.g. a
  token forged with `alg: none` or an asymmetric algorithm no longer
  verifies).

### FIX 2 — logout could revoke another driver's session (`src/routes/auth.ts`)

**Defect:** `POST /api/auth/logout` decoded the refresh token in the body and
revoked its `jti` unconditionally, without checking that the token belonged
to the authenticated caller (`req.auth.driverId`). An authenticated driver
who obtained (or guessed) another driver's refresh token could revoke that
driver's session.

**Fix:** the handler now decodes the refresh token, and only calls
`prisma.revokedToken.upsert` when the decoded `driverId` matches
`req.auth!.driverId`. If it doesn't match, or the token fails to verify, the
handler does nothing and still returns `204` (happy path and error path are
indistinguishable to the caller, which avoids leaking whether a given
refresh token exists/belongs to someone else).

### FIX 3 — unbounded JSON body size (`src/app.ts`)

**Defect:** `express.json()` had no size limit, so any endpoint accepting a
JSON body (login, refresh, logout, status update) would attempt to parse an
arbitrarily large request body.

**Fix:** `app.use(express.json({ limit: "1mb" }))`.

### Env wiring for fail-fast secrets

- `.env` and `.env.test` already had `JWT_ACCESS_SECRET="dev-access"` /
  `JWT_REFRESH_SECRET="dev-refresh"` from the original build (they were set
  even though Task 3's fallback made them technically optional at the time),
  so no change was needed there for local dev / ad hoc runs.
- `.env.example` no longer lists real placeholder values for the two secrets —
  it now documents just the variable names as comments (`# JWT_ACCESS_SECRET=
  # required — set a strong random secret, no default`), so nothing that
  looks like a usable secret ships in the example file.
- `vitest.config.ts` now also sets `process.env.JWT_ACCESS_SECRET ||=
  "test-access-secret"` and `process.env.JWT_REFRESH_SECRET ||=
  "test-refresh-secret"`, the same pattern already used for `DATABASE_URL`,
  so the test process has secrets available before `src/lib/tokens.ts` is
  imported anywhere (this is what makes the new fail-fast throw not break
  `npm test`).

### New tests added

- `tests/driver-trips.test.ts` — new test *"never returns another driver's
  trip as the caller's current trip"*: creates an in-progress trip for driver
  B, calls `GET /api/driver/trip/current` as driver A, and asserts the body
  is exactly `{ success: false }` (not just "no crash" — the IDOR-adjacent
  read path for `/trip/current`, previously only covered for
  `/trips/active`).
- `tests/auth-session.test.ts` — extended the existing *"rotates the refresh
  token"* test: after the first rotation succeeds, it now also replays the
  original (pre-rotation) `refreshToken` against `POST /api/auth/refresh` and
  asserts `401`, confirming single-use/rotation is enforced and not just that
  a new token is issued.
