## What was built

- **Roles/auth**: `signAccess`/`signRefresh` unchanged in signature, now embed `role:"driver"`; added `signDispatcherAccess`/`signDispatcherRefresh`. `requireAuth` sets `req.auth = { driverId, dispatcherId?, role }`. New `requireDispatcher` → 403 unless `role==="dispatcher"`. `/api/auth/refresh` and `/api/auth/logout` now branch on the token payload's role so both identities share rotation/revocation.
- **Schema** (migration `be4_dispatcher`): `Trip.driverId` → `String?` (FK `ON DELETE SET NULL`, existing data preserved), added `approvedAt`/`approvedBy`; new `Dispatcher`, `RoutePreAssignment`, `DriverLocation` models.
- **Routes**: `src/routes/dispatcherAuth.ts` (`POST /api/auth/dispatcher/login`), `src/routes/dispatcherDrivers.ts` (driver + vehicle CRUD, driver location history), `src/routes/dispatcherTrips.ts` (trip create/list/get/assign), `src/routes/dispatcherApprovals.ts` (trip + signs-proof approve/reject, fleet locations + overview). All mounted at `/api/dispatcher` behind `requireAuth` + `requireDispatcher`.
- **tests/helpers.ts**: added `createDispatcher()` and `loginDispatcher()`; `resetDb()` extended to clear the three new tables.

## Bugs found and fixed along the way

1. **Type regression risk**: making `req.auth.driverId` optional broke `tsc` across ~12 existing driver routes that read `req.auth!.driverId` without narrowing. Fixed by keeping `driverId` non-optional in the type and filling a sentinel empty string (`""`, never a valid driver uuid) for dispatcher-authenticated requests — this also closes a real hole: Prisma silently *drops* `undefined` filter values, so `driverId: undefined` on a dispatcher token would have stripped the ownership filter out of driver-scoped queries entirely (a dispatcher token could otherwise have walked through `/api/driver/*` and `/api/trips/*` routes unfiltered). Verified with a dedicated regression test that a dispatcher token hitting `/api/driver/trips/active` returns `[]`, not another driver's data.
2. **Public login route shadowed by broad middleware**: `signsProofRouter`, `messagesRouter`, `notificationsRouter`, and `vehicleRouter` are mounted at the bare `/api` prefix and each does `router.use(requireAuth)` with no path filter — meaning that once *any* `/api/*` request reaches one of them, `requireAuth` runs unconditionally for it, whether or not that router actually owns a matching route. `POST /api/auth/dispatcher/login` was originally mounted after these, so it 401'd before ever being matched. Fixed by mounting `dispatcherAuthRouter` (and the other dispatcher routers) immediately after the existing `authRouter`, ahead of the broad `/api`-mounted ones. Confirmed via a standalone repro script before touching the test suite.

## Judgment calls (not fully specified in the plan)

- The plan's "Fleet reads" section (`GET /dispatcher/locations`, `GET /dispatcher/drivers/:id/locations`) referenced driver location data that no existing model captured. Added a minimal `DriverLocation` log-style model (no Prisma relation, matching the existing `SafetyAlert`/`FuelLog`/`Incident` convention) — tests populate it directly via Prisma, the same pattern the existing test suite already uses for trips/stops.
- Trip approve sets status to `"approved"` (matching the `approvedAt`/`approvedBy` field names); reject sets `"rejected"`. The plan's wording ("status `assigned`/`approved`") was ambiguous; `"approved"` was chosen for consistency with the new fields and because driver-visibility already happens at `assign` time per the acceptance-test flow, not at `approve` time.
- `reason` on trip/signs-proof reject is validated but not persisted (no schema field exists for it) — same "accept but don't store" pattern already used elsewhere in this codebase (e.g. `checklistCompleteSchema`'s unused `loadId`/`populate`).
