  - `dispatcherApprovals.ts` trip approve → `status_change` (only when the trip has a `driverId`).
  - `dispatcherApprovals.ts` signs-proof approve/reject → `signs_proof_approved` / `signs_proof_rejected`, recipient resolved via a small `signsProofDriverId(stopId)` helper that walks stop → trip → driverId (SignsProof carries no driverId directly).

Covers: valid-token connect, missing-token 4401, invalid-token 4401, ping/pong, trip_assignment delivery on dispatcher assign (via `fetch` against the same live server), trip_assignment→route_pre_assignment ordering, and driver-isolation (B never receives A's event). `tests/realtime-helpers.ts` adds a FIFO message collector that buffers frames from connection time — needed because two emits sent back-to-back in one handler can both flush before a second `ws.once("message")` listener is registered, silently dropping the second frame with naive one-shot listeners. Sockets + server are closed in `afterEach`.

**Concerns:**
- The plan's fourth emit point — "notification create → `general_notification`" — has no target: there is no notification-creation endpoint anywhere in the current backend (`prisma.notification.create` is not called anywhere; `notifications.ts` only reads/marks-read). Rather than invent a new dispatcher endpoint out of scope for this task, I left this emit point unwired. `emitToDriver` is exported and ready to use the moment such an endpoint exists — it's a one-line call away.
- `verifyAccess` returns a union (`{driverId,...}|{dispatcherId,...}`); the plan's literal snippet (`verifyAccess(token).driverId`) doesn't type-check under this repo's `strict: true`. Fixed by checking `payload.role !== "driver"` first and treating that as unauthorized (a dispatcher access token cannot open a driver realtime socket), consistent with the "driver access tokens carry driverId; that's the socket identity" instruction.
