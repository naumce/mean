## Deviations from the plan
- **multer version**: plan didn't pin a version; installed `multer@^2.0.0` (2.x is what's on the registry as current; the commonly-cited `1.4.5-lts.x` line still exists but 2.x has no known advisories against it and the subset of the API used — `diskStorage`, `.single()` — is unchanged).
- **`src/routes/signsProof.ts` mount point**: the plan says "new `src/routes/signsProof.ts`; mount in `app.ts`" without addressing that its two endpoints (`/api/mobile/trips/:id/signs-proof-requirements` and `/api/signs-proof/:stopId/upload`) share no common URL prefix. Resolved by mounting the router at `/api` and giving each route its full sub-path inside the file, rather than splitting into two separate router exports/mounts.
- **`@types/express` v5 vs `express` v4 param-typing quirk**: pre-existing in the foundation (not introduced by BE-2), but newly triggered here because this is the first time route-param paths (`:id`, `:stopId`) are combined with a second generic middleware (`validateBody`, `multer.single`) in the same route registration. That combination widens `req.params.*` to `string | string[]` under `@types/express`'s repeated-param typing even though a single named segment is always a plain string at runtime. Fixed with a narrow, commented `as string` cast at each affected call site (4 total: `checklist/complete`, both upload routes, `signs-proof/:stopId/upload`) rather than changing the shared `Request`/router types.
- **`checklist/complete` behavior**: the plan's body shape `{loadId?, populate?}` is accepted and validated but the endpoint doesn't do anything conditional on `populate` (e.g., seeding default checklist items) since the plan/contract doesn't specify what to populate from; it simply marks all existing `ChecklistItem`s for the trip complete and flips `preTripCheckCompleted`. Flag this if the mobile client expects auto-seeded items.
- **Photo/document upload response**: returns exactly `{url}` per the contract table; the created `Upload` row's other fields (`id`, `kind`, `mimeType`) are persisted but not echoed back, matching the plan's literal "returns `{url}`" wording.
