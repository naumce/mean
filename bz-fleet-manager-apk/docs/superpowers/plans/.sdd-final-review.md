## Critical

## Important

1. **`src/lib/tokens.ts:3-4` — hardcoded fallback JWT secrets (`"dev-access"` /
   `"dev-refresh"`).** If `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` are unset in
   production, the app silently signs and verifies tokens with these publicly-known
   values (they are committed in `.env.example`). Anyone who knows them can forge an
   access token for any `driverId`, which defeats the entire authorization-by-
   construction guarantee (every scoped query trusts `req.auth.driverId`, which comes
   from the token). No startup validation asserts the secrets are present. **Fix:**
   fail fast at boot if either secret is missing; remove the `?? "dev-*"` fallbacks.
   This is the single must-fix before this is a production auth foundation.

2. **`src/routes/auth.ts:36-43` — logout revokes any refresh token by `jti` without
   checking it belongs to the authenticated caller.** The handler decodes the supplied
   refresh token and revokes its `jti`, but never compares its `driverId` to
   `req.auth.driverId`. An authenticated driver who obtains another driver's refresh
   token can revoke that driver's session (session-DoS). Low likelihood (requires
   possession of the victim's refresh token) but trivial to close: verify
   `decoded.driverId === req.auth!.driverId` before revoking.

3. **`src/routes/auth.ts:12` — no rate limiting / brute-force protection on login**
   (or on refresh). The login endpoint bcrypt-compares on every attempt with no
   throttling. Per the project's own security rules ("rate limiting on all
   endpoints"), an auth foundation should ship with at least login throttling. Fair to
   defer, but should be tracked, not silently omitted.

## Minor

4. **`src/lib/tokens.ts:10-11` — `jwt.verify` does not pin `algorithms`.** With
   jsonwebtoken v9 the `none` algorithm is rejected by default so there is no active
   bypass, but pinning `{ algorithms: ["HS256"] }` is cheap defense-in-depth against
   future config drift.

5. **`src/app.ts:8` — `express.json()` has no body-size limit.** Unbounded request
   bodies on public POST endpoints are a minor DoS surface; set a `limit`.

6. **`RevokedToken` grows unbounded.** `expiresAt` is stored (`src/routes/auth.ts:30,40`)
   but nothing purges expired rows, so the revocation table only grows. Not wrong, but
   needs an eventual cleanup job.

7. **Test gap — `GET /driver/trip/current` has no direct cross-driver isolation test.**
   The genuine isolation assertion (`tests/driver-trips.test.ts:20-27`) exercises
   `/trips/active`; `/trip/current` shares the identical scoping pattern but is only
   tested for the happy path (`tests/driver-trips.test.ts:11-18`). Add a negative case
   for parity.

8. **Test gap — normal refresh rotation does not assert the old token is now rejected.**
   `tests/auth-session.test.ts:17-23` asserts the new token differs; single-use of the
   rotated-away token is only proven indirectly via the logout-revoke test
   (`:25-30`). A `refresh(old) -> refresh(old)` second call expecting 401 would nail
   down single-use explicitly.

9. **`tests/helpers.ts:16` — `createDriver` default `passwordHash: "x"`.** Harmless for
   token-based tests (they mint tokens via `signAccess`), but a plaintext non-bcrypt
   hash could mask a real verify bug if reused in a login test; login tests correctly
   use `hashPassword` instead, so this is informational only.
