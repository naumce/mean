# dispatch-v2 A/B Experiment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use `- [ ]`.

**Goal:** A second prompt version, `dispatch-v2`, that forces a disciplined candidate comparison (discover feasible candidates → investigate at least two → compare with structured strengths/weaknesses/unknowns → evidence-graded confidence), enforced by protocol validation derived from tool evidence, and an A/B report of dispatch-v1 vs dispatch-v2 on scenarios A–H with the same `qwen3:8b`.

**Architecture:** the harness gains ONE additive seam — a prompt-profile registry (`src/lib/aiHarness/prompts/index.ts`): `promptVersion → { version, system, user(), nudge, terminalDefinition, validate(raw, ctx) }`. The loop resolves the profile from the run's `promptVersion` (already persisted per experiment/run) instead of hard-coding v1. `dispatch-v1`'s texts, terminal schema and validation stay byte-identical. `dispatch-v2` adds the `comparison` field to the terminal output and a protocol validator that inspects the run's persisted tool steps (not the model's prose). Everything else — model config defaults, tools, projections, ranking, seed, scenarios, loop protection — is untouched.

**Spec:** the product owner's brief (2026-09-25, "Build dispatch-v2 as a NEW prompt version", items 0–9) — binding.

## Global Constraints
- Untouched: `prompts/dispatch-v1.ts` (byte-identical — add a test that hashes its `system` text against the current value), `loop.ts` protection/termination logic, `config.ts` defaults, `dispatchTools/*` (incl. `invoke.ts`'s projection), `domain/dispatch/*`, `seed-world*`, scenarios, `ollamaAdapter.ts`, schema (no migration — `promptVersion` columns already exist).
- The loop's only change: resolve `PromptProfile` by `promptVersion` and call `profile.validate` / use `profile.terminalDefinition` / `profile.system|user|nudge`. Unknown version → `internal_error` with a clear message.
- Protocol facts come from persisted `tool_call`/`tool_result` steps with `ok: true` — never from model text.
- No exposure to the model of: scenario expectations/hints (already stripped), deterministic ordering or top candidate, human decisions, previous runs' decisions. v2 text must not contain "score", "rank", "ranking", "deterministic", "scenario", "expected", "engine", "winner".
- Neither prompt is labelled "better" anywhere (code, report, doc).
- Implementers: no git writes, no subagents, never read/print `.env`; no process narration in comments.
- Checks: backend targeted vitest + `npx tsc --noEmit` + full suite once (baseline 188 files / 1915); portal `npx vitest run` (baseline 123 / 1353) + `vue-tsc` + build.

```ts
// prompts/index.ts
export interface ProtocolContext { orgId: string; loadId: string; feasibleDriverIds: ReadonlySet<string>; steps: StoredStep[] /* persisted so far */ }
export interface PromptProfile { version: string; system: string; user(args: { loadId: string; loadRef: string | null }): string; nudge: string; terminalDefinition: ToolDefinition; validate(raw: unknown, ctx: ProtocolContext): Promise<ProposalCheck> }
export const PROMPT_PROFILES: Record<string, PromptProfile>;   // { "dispatch-v1": …, "dispatch-v2": … }
export const PROMPT_VERSIONS: string[];
export function resolvePromptProfile(version: string): PromptProfile | null;
// dispatch-v1 profile: system/user/nudge = DISPATCH_PROMPT_V1 verbatim; terminalDefinition = PROPOSE_DECISION_DEFINITION; validate = validateProposal(raw, { orgId, feasibleDriverIds }) — ctx.steps ignored.
// dispatch-v2.ts
export interface ComparisonEntry { driverId: string; strengths: string[]; weaknesses: string[]; unknowns: string[] }
export interface ProposalV2 extends Proposal { comparison: ComparisonEntry[] }
export const PROPOSE_DECISION_V2_DEFINITION: ToolDefinition;   // v1 parameters + comparison (array of {driverId, strengths[], weaknesses[], unknowns[]}, required)
export const proposalV2Schema: z.ZodType<ProposalV2>;   // v1 rules + comparison 1..6 entries, strings 3..300 chars, arrays ≤ 8 items each (may be empty)
export const DISPATCH_PROMPT_V2: { version: "dispatch-v2"; system: string; user: (a) => string; nudge: string };
// protocol.ts
export interface Investigation { driverId: string; tools: string[] /* distinct successful tool names for this driver */; covers: { availability: boolean; location: boolean; deadhead: boolean; hos: boolean; equipment: boolean; metrics: boolean; lane: boolean; response: boolean; preferences: boolean } }
export function investigationsFromSteps(steps: StoredStep[], loadId: string): Map<string, Investigation>;   // successful tool_result steps whose matching tool_call had a driverId argument: getDispatchCandidateDetails(loadId match) covers availability, location, deadhead, hos, equipment, lane, response, preferences (metrics partially: onTimeRate/responseRate → response, lane); getDriverAvailability → availability, location; getDriverMetrics → metrics, lane, response; getDriverHistory → lane; getDriver → equipment; getDriverLocationHistory → location. A driver counts as INVESTIGATED when covers.availability && (covers.metrics || covers.response) && (covers.deadhead || covers.hos) — i.e. getDispatchCandidateDetails alone qualifies, or getDriverAvailability + getDriverMetrics, or getDriver + getDriverAvailability + getDriverMetrics; state this table in the doc comment.
export function checkProtocolV2(proposal: ProposalV2, ctx: ProtocolContext): string[];   // errors, model-readable:
//  - if ctx.feasibleDriverIds.size >= 2: at least 2 DISTINCT feasible candidates investigated; otherwise "You have investigated N feasible candidate(s) (<names/ids>). Investigate at least one more feasible candidate before proposing — for driver <id> call getDispatchCandidateDetails (load <loadId>) or getDriverAvailability and getDriverMetrics."
//  - every comparison.driverId ∈ feasible set and investigated; the proposal.driverId (when not null) appears in comparison; comparison has ≥ min(2, feasible count) entries;
//  - confidence band: confidence ≥ 0.90 while the chosen driver's comparison entry has any unknowns → "Confidence 0.90+ requires very little relevant uncertainty; you listed unknowns for the chosen driver. Lower the confidence or resolve the unknowns with tools." ; confidence ≥ 0.70 while the chosen entry has ≥ 3 unknowns → same family of message.
//  - duplicates in comparison rejected.
```
Loop wiring: `RunInput.promptVersion: string` (runner passes the run's persisted `promptVersion`, defaulting to the experiment's); the profile's `terminalDefinition` is what goes into `tools`; `handleProposeCall` calls `profile.validate(args, { orgId, loadId, feasibleDriverIds, steps: await store.listSteps(decisionId) })`; on success the persisted `proposedDecision` is the full validated object (incl. `comparison` for v2). Stats gain `candidatesInvestigated: number` (from `investigationsFromSteps` at finalize, counting investigated feasible drivers) for every version. Evaluation rows gain `promptVersion`, `candidatesInvestigated`; summary gains `meanCandidatesInvestigated`, `meanConfidence`, `confidenceBands: { "≥0.90": n, "0.70–0.89": n, "0.50–0.69": n, "<0.50": n }`, `repeatedPick: { driverId, name, share } | null` (most-picked driver's share of proposed runs).
`dispatch-v2` system text — the required content, in this order, plain sentences, ≤ 550 words: role and task; the disciplined process (1 discover feasible candidates with findFeasibleDrivers; 2 investigate at least two feasible candidates whenever two or more exist; 3 for each finalist obtain the AVAILABLE evidence for current/projected availability, current/projected location, deadhead and pickup feasibility, HOS result, equipment and qualification compatibility, driver metrics, lane experience, response history, relevant preferences — name the tools that provide each; state that missing information is recorded as an unknown, never invented or required); 4 compare finalists in the `comparison` field before selecting — strengths, weaknesses, unknowns, as evidence, not names; 5 the confidence bands verbatim (0.90–1.00 exceptionally strong evidence, very little relevant uncertainty; 0.70–0.89 strong recommendation with some uncertainty; 0.50–0.69 reasonable preference but meaningful uncertainty; below 0.50 weak evidence or insufficient differentiation) and "confidence measures evidence strength, not how certain you sound; do not default to 0.95 or 1.0"; 6 the explicit rules: proximity alone does not determine the best driver; historical reliability alone does not determine the best driver; preferences are not hard feasibility constraints; the feasibility results returned by the tools are authoritative; never invent missing facts; investigate before deciding; compare evidence, not driver names; do not infer quality from demographic or profile characteristics (name, language, home base); 7 finish with exactly one `propose_decision` including `comparison`; `driverId: null` allowed with the reason. Nothing about scores, ranks, order, expected drivers or prior decisions. `nudge` reminds of the investigation requirement and the terminal call.
Routes: `POST /ai/experiments { …, promptVersion?: string }` (must be in `PROMPT_VERSIONS`, default "dispatch-v1"), `PATCH` may change it only when the experiment has no runs (409 otherwise); `GET /ai/status.promptVersions = PROMPT_VERSIONS`. Runs snapshot `promptVersion` from the experiment at enqueue (already stored) and the loop uses the RUN's value.
Scripts: `ai-eval-scenarios.mjs` gains `AI_EVAL_PROMPT` (default `dispatch-v1`), `AI_EVAL_RUN_LABEL` (default `1`), `AI_EVAL_EXPERIMENT_NAME` override; creates the experiment with `promptVersion`; output file `docs/evaluations/<date>-<prompt>-run<label>.md`. New `ai-compare-prompts.mjs`: env `BASE_URL`, `AI_COMPARE_V1_IDS`, `AI_COMPARE_V2_IDS` (comma-separated experiment ids) — pulls each experiment's evaluation, prints and writes `docs/evaluations/<date>-dispatch-v1-vs-v2.md`: per scenario (one row per run, grouped by prompt): pick, deterministic top, confidence, turns, tool calls, unique tools, candidates investigated, invalid calls, termination, duration s, tokens; aggregates per prompt: completion rate (proposed/runs), engine agreement rate (matched top / proposed), mean candidates investigated, mean turns, mean tool calls, mean confidence, confidence distribution (the four bands), repeated-driver-selection frequency (share of proposed runs picking the most-picked driver, and the driver). Neutral wording; the header states both prompts ran the same model and config and that the table is behavioural data, not a verdict.
