- `src/stores/trips.ts` (+ `trips.spec.ts`) — `useTripsStore`: `list(filters?)`, `get(id)`, `create(payload)`, `assign(id, driverId)`; `items`, `current`, `loading`, `error`. Mirrors the `vehicles`/`drivers` store pattern exactly.

- `src/router/index.ts` — added `/trips` (`trips`), `/trips/:id` (`trip-detail`), `/approvals` (`approvals`).
- `src/layouts/AppShell.vue` — activated the Trips and Approvals sidebar links (previously disabled "Soon" placeholders).

## Notes / concerns
- `RouterLink` (used for the trip identifier link in `TripsView`) throws at mount time if no router plugin is installed (confirmed with a throwaway repro), so `TripsView.spec.ts` mounts with `global: { stubs: { RouterLink: RouterLinkStub } }`. No other spec needed this.
- `TripDetailView` has no dedicated component spec, per the plan's test list (only `trips.spec.ts`, `approvals.spec.ts`, `StatusPill.spec.ts`, `ApprovalsView.spec.ts`, `TripsView.spec.ts` were required). It was still built and type-checks/builds cleanly; verified manually by reading the code, not by an automated test.
- No backend was available to hit; all verification is against mocked `api`/store calls, consistent with the rest of the portal's test suite.
